Anthropic: Claude produced formal proofs of memory safety for 239 fuzz targets across 123 libraries

Anthropic, working with Theorem, reports that Claude turned each library's existing fuzz test into a specification (the target never crashes on any input under 64 MB) and then proved it at the RISC-V assembly level, checked by the Rocq proof assistant. According to the write-up, Claude produced about one billion lines of Rocq, of which roughly 180 million passed the checker; a typical proof runs about 600,000 lines. Anthropic says the attempts surfaced hundreds of bugs, including ones a fuzzer would rarely hit, such as an out-of-bounds write that needs a roughly 20 MB input with one rare layout.

Anthropic is explicit about limits: the proofs cover single-threaded static RISC-V binaries linked against musl, not the x86 or ARM glibc builds most people run, and AddressSanitizer does not catch every memory bug. Theorem is offering the pipeline free to qualifying open-source projects through its OSS Verify program. Link is a third-party summary of Anthropic's post.

Safety · Oct 22 · 183 points on HN
How does Fable 5.1 hide messages in images?

Researchers from the SASH Fellowship asked Claude Fable 5.1, at maximum effort, to draw an SVG hiding each of 50 short messages in 15 languages, with no scheme specified. In 33 of 50 images the model encoded letters as object heights, such as building heights in a night skyline, and a fresh Fable instance given only the rendered PNG recovered 78% of the messages. GPT-6 Astra, given the same task, never used heights; it favoured Morse-style short and long objects and acrostics, and cross-model decoding recovered 44 of Fable's 50 and 42 of Astra's.

The authors say decoding is still easy to catch by watching the decoder's tool calls, so they do not claim it is dangerous today, but they frame it as a possible precursor to image steganography between agents.

Open Weights · Oct 23 · 353 points on HN
Kimi K3.1 Pro and K3.1 Pro Highspeed

Moonshot calls K3.1 Pro its most capable 3T-class open-weight model, with a 1M-token context window, and says the Highspeed variant runs 2–3× faster. Both are live on Kimi.ai, Kimi Code and the API, with full weights promised by Nov 4. Moonshot reports 65.7% on Terminal-Bench 4.0 against 66.4% for Claude Opus 5.5 and 58.2% for GPT-6 Astra, and says claim-level hallucination on its internal stress test fell from 23.4% to 8.3%.

Artificial Analysis, publishing today, scores it 55 on its Intelligence Index, fourth behind Opus 5.5 (58), Sonnet 5.5 (56) and Muse Wonder Full (56), and reports 2.8T total and 104B active parameters. It measures a cost per task of $1.98, roughly level with K3, because K3.1 Pro uses 14% more output tokens while first-party prices are 33% lower ($2 input, $10 output, $0.20 cached per million). Artificial Analysis says the open-weights gap to proprietary models would narrow from 12 points to 3 once weights ship. Moonshot also says it removed cyber-related data from training for the open release.

API · Oct 22
OpenAI makes the Decisions API generally available

OpenAI's /v1/decisions endpoint, backed by GPT-6 Luna, returns typed answers instead of free text: a probability for a yes/no predicate, a choice among fixed options with per-option probabilities and a confidence value, or a rubric score. OpenAI says it is up to 10× faster than asking Luna through the Responses API and bills only input tokens, at $0.10 per million ($0.01 cached). Since the beta it added prompt caching, JSON inputs, up to 400 questions per request, EU and US residency, and a GPT-Live integration for voice sessions.

Customer figures quoted by OpenAI are self-reported: Sierra says next-action selection runs under 280 ms p95, about 3× faster and 90% cheaper per call than its prior approach with no drop in outcomes, and Datadog reports 40× faster p95 when scoring agent-generated shell commands. See Flip Tech Watch.

🛠️ Flip Tech Watch
Flip Tech Watch · Oct 22
A typed, calibrated decision endpoint for in-call routing

The Decisions API (above) returns probabilities for fixed answer sets at $0.10 per million input tokens, and OpenAI describes a support-agent pattern in which decisions run on transcript updates to choose between asking a clarifying question, routing, or escalating.

Flip angle: This maps directly onto intent classification, the "escalate or keep automating" call, and flagging returns or order-status calls that need a human. Per-option probabilities could also give a threshold tied to logged outcomes, rather than a self-reported confidence. Caveats: the speed and cost figures come from OpenAI and its customers, it is a single-vendor endpoint, audio is not supported (transcripts only), and dependent decisions need separate calls. First test: replay a few thousand logged escalated calls through a choice question using Flip's intent list plus an "other" fallback, and compare accuracy and p95 latency with the current router.

Keypad payment capture without leaving the call

Sierra's design hands card entry to the caller's keypad and Stripe while the agent steps out of the audio path, then resumes to confirm the result.

Flip angle: For ecommerce and retail clients, calls about order changes, reorders, or outstanding balances currently end with a payment link or a transfer to a live agent. Caveats: this is a competitor's product announcement with one customer's self-reported figure, from healthcare billing rather than retail, and PCI scope, client opt-in and the payment processor each client uses would decide feasibility. First test: count how many escalated calls in a client's logs ended in a payment or order change.

🧠 Today's Lesson
Classification without generation: how a model can answer in one forward pass

Chat-style generation is a loop: run the whole prompt through the model once (prefill), then produce one token at a time, re-reading the weights and the KV cache for each. That loop is where most latency lives. A task with a fixed set of answers does not need it.

At the end of any forward pass the model produces a score, a logit, for every token in its vocabulary. A softmax turns those scores into probabilities. If the answer options are labelled with distinct single tokens, say "A", "B", "C", reading the probabilities of just those tokens after prefill gives a full probability distribution over the options, with zero decode steps. One pass instead of dozens.

This also explains where trustworthy confidence numbers can come from. The probability is read from the model's actual output distribution rather than written out as text, which is the weakness of asking a model to type "0.85". It is still only as good as its calibration, so thresholds should be set against labelled outcomes, as OpenAI's own documentation advises for the Decisions API. OpenAI has not published how that endpoint is implemented, so the single-pass mechanism here is the general technique, not a description of its internals.

Two practical consequences: prefill is compute-bound and batches well, so cost scales with input tokens (matching an input-only price), and a long shared prefix such as the category descriptions can be cached and reused across calls.
