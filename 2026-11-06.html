Thinking Machines introduces Inkling 2 Small, a 594B-parameter MoE with 17B active, weights due next week

Thinking Machines Lab describes its second model generation as a mixture-of-experts model with 594B total and 17B active parameters, image input and variable reasoning effort. It scores 31 on the Artificial Analysis Intelligence Index, which the lab says far exceeds its earlier models. It is initially available on the lab's Tinker platform with closed weights; the lab says it intends to release the full weights under Apache 2.0 next week, after external safety testing and red-teaming.

The lab reports 86.3% on SWEBench Pro v2 (Hard), 72.1% on DeepSWE v1.1 and 81.6% on MMMU Pro, and says the model was trained with RL on hundreds of thousands of long-horizon coding tasks. In one demo, the model autonomously post-trained Qwen3.5-4B on Tinker for time-series forecasting over 4.5 hours and $426 of spend, more than doubling that model's forecasting score. All results are the lab's own.

Research · Nov 5
Anthropic studies 207,000 research sessions to see how scientists use Claude

The economics team reports that data analysis accounts for about one-third of Claude sessions and nearly half of Claude Code sessions, while idea generation and data gathering are used less even though surveyed scientists rank them as most important for discovery. Use is higher in computer science, mathematics and statistics than in lab-based sciences.

In a simple scenario model, Anthropic estimates that full automation of non-physical research work could raise output in fields such as computer science up to 15-fold, versus three- to fourfold in bench sciences. About 40% of surveyed AI-using researchers expect models to run full projects on their own by 2030.

NVIDIA publishes NVKE, an Apache-2.0 management plane for Kubernetes on bare-metal GPUs

The repository describes a preview-status service for running managed Kubernetes on a team's own NVIDIA GPU infrastructure, with each workload cluster getting its own control plane, etcd and node pools. Nodes attest through SPIFFE/SPIRE using TPMs before receiving join credentials, and provisioning goes through NVIDIA Infra Controller (NICo), the only compatible provider at preview. The README says it is not recommended for production.

Inkling 2 Small's autoresearch demo: a small model fine-tuned by an agent for time-series forecasting

Thinking Machines says Inkling 2 Small wrote its own evaluator, curated data and ran SFT and RL on Qwen3.5-4B via Tinker, cutting forecast error on electricity demand by 67% and Wikipedia page views by 20% versus the base model, for $426 over 4.5 hours. The lab says weights arrive next week under Apache 2.0.

Flip angle: Call-volume forecasting for ecommerce clients and staffing around seasonal peaks is the same shape of task: hourly or daily series with a clear error metric. A small fine-tuned forecaster could be cheaper than a large general model. Caveat: the demo used public data and the lab's own benchmarks, and one series (air quality) got 3% worse; the first test would be backtesting on a few clients' historical call counts against a simple seasonal baseline.

🧠 Today's Lesson
Prefix caching: why a long system prompt only has to be computed once

Before a model generates its first token, it runs prefill: a pass over the whole prompt that computes a key and value vector for every token at every layer. These form the KV cache. Prefill cost grows with prompt length, and it is the main contributor to time-to-first-token.

Many requests share the same opening. A voice agent, for instance, sends the same instructions, tool definitions and knowledge-base excerpt on every turn, and only the last few lines change. Because attention in a decoder is causal, the KV entries for a token depend only on tokens before it. If two prompts start with an identical sequence, those entries are identical and can be reused.

Prefix caching does exactly that. Engines such as vLLM and SGLang split the KV cache into fixed-size blocks, hash each block together with everything before it, and keep finished blocks in a lookup table. A new request is matched block by block against the table; the matching prefix skips prefill and only the new tail is computed. Hosted APIs expose the same idea as prompt caching, typically billing cached input tokens at a discount.

Two practical rules follow. The match must be an exact prefix, so one changed character early in the prompt invalidates everything after it: put stable content (instructions, tools, documents) first and volatile content (timestamps, user text) last. And cached blocks occupy GPU memory, so a busy server evicts the least recently used ones; hit rate is worth logging, since it directly predicts latency and cost.
