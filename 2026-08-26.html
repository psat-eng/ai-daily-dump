🔥 What's Hot Right Now
GLM-5.3-Flash drops — and r/LocalLLaMA has a full megathread
z.ai · r/LocalLLaMA megathread · HN #12, 354 pts · Released today
Z.ai's first open-weight release of the glm5_next architecture, and the most technically dense drop in a while. Key points engineers are digging into:

Architecture: 45 layers in repeating blocks — 3× KDA linear attention followed by 1× DeepSeek-style sparse attention (34 linear / 11 sparse total). The sparse layers use a "lightning indexer" with a top-k budget of 2048 tokens, sharply reducing long-context serving cost vs. full attention.

Natively multimodal: A 24-layer ViT (448px, patch 14, 2×2 spatial merge) with temporal patching handles both image and video tokens in the same vocabulary — trained on a 30T-token multimodal corpus.

MTP head ships in the weights: One next-N prediction layer is baked into the checkpoint. The official vLLM recipe uses it with k=5 speculative tokens out of the box. (See today's lesson for how this works.)

FP8 by default: main repo is e4m3 FP8 with dynamic activation scaling; a separate BF16 repo exists for hardware that can't do FP8. Z.ai's pitch: outperforms GLM-5.2 at one-tenth the price, approaching Claude Opus 4.8 on coding and agentic benchmarks.
Qwen3.8-Flash-Next: a live preview of the Qwen4 architecture
qwen.ai · HuggingFace (weights live) · HN #13, 360 pts · Released today
Alibaba's Qwen team shipped Qwen3.8-Flash-Next today — not a production model but an explicit architectural preview of what Qwen4 will look like. Key numbers: 125B total parameters, 6B active per token (MoE), 262K native context extendable to 1M.

Two headline architectural changes: GDN hybrid architecture (upgraded attention, residual, embedding and optimization paths) and Qwen Sparse Attention (QSA), their own take on sliding-window + top-k sparse attention to cut long-context costs. They're releasing this early so tool builders, quantizers, and inference engine maintainers can adapt their code before Qwen4 lands.

Unsloth already has GGUF quants up on HuggingFace. Worth benchmarking against GLM-5.3-Flash on your workloads — two big architectural previews landing the same day is unusual.

📖 Today's Lesson
MTP Heads: How Models Become Their Own Draft Models for Speculative Decoding

Standard speculative decoding requires a separate small "draft" model that proposes k tokens, which the main model then verifies in a single parallel forward pass. The friction: you need to load, serve, and schedule that draft model independently, and if the draft model is too different from the main model, acceptance rates tank.

Multi-Token Prediction (MTP) heads solve this by baking the draft model directly into the checkpoint. During training, auxiliary prediction heads are attached after the final transformer block — one head per speculative position. Each head is trained to predict the token at position +n using a small MLP or shallow transformer. They share the same hidden states as the main model, so no extra KV cache or batch-splitting is needed at inference.

At serving time, the MTP heads run on the same forward pass that already computed the main model's next-token logits, producing draft tokens essentially for free. The main model then verifies all k proposals in one speculative step. DeepSeek-V3 popularized this pattern; GLM-5.3-Flash ships one MTP head in its weights today, and the official vLLM config uses it with speculative_tokens=5.

The gotcha to know: longer speculative chains hurt at long context. GLM's benchmarkers found k=7 drops throughput from 76 to 55 tok/s at 65K tokens — verification cost grows faster than the draft gains. The rule of thumb: use k=3–5 for typical workloads, drop to k=2–3 when serving long-context requests. Dial it per deployment, not globally.
