What's Hot Right Now

Qwen3.8-27B: 24% at big-number addition without reasoning, 99% with it

Oct 4 · Simon Willison · local run on a DGX Spark

Simon reran an old GPT-4o "add two numbers, answer in words" experiment on Qwen3.8-27B (Q4_K_M GGUF). With reasoning off it scored 23.57% overall (1,195 of 5,070 cases), falling to 6.44% on ten- to thirteen-digit operands. With reasoning on, a one-shot pilot got 167 of 169 right, and the traces show the model lining up digits and carrying column by column. A neat, concrete demo of what the thinking budget buys a small quantized model.

"We're going to need default hard budget caps on pretty much everything"

Oct 3 · Simon Willison · also circulating on Hacker News

His argument: usage-billed APIs should ship with hard spend limits that cut service off, not warning emails, because coding agents make it easy to deploy something that quietly runs up a bill. He cites AWS spending limits (announced September) and Google Cloud Spend Caps (July) as steps in the right direction. Worth thinking about for any agent loop you run against metered APIs.

Today's Lesson

Why temperature 0 isn't deterministic: batch-invariant inference

You set temperature to 0, send the same prompt twice, and sometimes get different text. The usual suspect is "GPU randomness", but the real cause is quieter: floating-point addition isn't associative, so (a + b) + c can differ from a + (b + c) in the last bits.

Inside a transformer, matmuls, attention and normalisation all sum long lists of numbers, and the GPU kernel picks how to split and order that sum. Well-tuned kernels choose differently depending on batch size and sequence layout. With continuous batching, your request lands in a different batch each time depending on server load, so the reduction order changes, the logits shift by a hair, and two near-tied tokens can swap places. After one flip, everything downstream diverges.

The fix is batch-invariant kernels: fix the reduction strategy so a given row produces identical bits whatever else is in the batch. It costs some throughput, which is why it's usually opt-in. The digest above mentions vLLM work on exactly this.

Why care: reproducible evals, RL training where sampler and trainer must agree, and debugging agent regressions you can't replay.
