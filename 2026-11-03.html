Debate · Nov 3 · 643 points on HN
spaCy author: the "Astra can read and write weights to improve Qwen" post is misleading

Matthew Honnibal argues that the weight-space-programming paper bundles unlike experiments under one headline. By his table, the "just by looking at the raw weights" setting (raw floats in context, no tools, no running the network) appears only in three experiments on networks of 17K to 172K weights. Every experiment on a real language model uses Python, and the headline Qwen3.5-0.8B result, MATH-500 from 7.9% to 48.1%, also lets the model run up to 50 batches of practice problems.

Honnibal says the Qwen result shows Astra can be prompted to do what a human ML engineer does when scripting analysis and edits of weights. He also lists failures: the same approach did not work on Gemma 3 270M, and the from-scratch game networks beat PPO at 500M steps only on Breakout. The post is dated Nov 3.

Local models · Nov 3
Qwen 3.8 27B on a laptop identifies games from raw network weights, slowly

Simon Willison reran the paper's no-tools "which game was this network trained on?" prompt with Qwen 3.8 27B (a 17GB quant in LM Studio). It named Pac-Man, Pong and Breakout correctly with stated confidence of 72%, 75% and 88%, taking 46 minutes (43,506 reasoning tokens), 65 minutes and 52 minutes respectively, and failed on Freeway. A default 8192-token context failed with errors, so a long context window was required. Willison notes that Kimi K3.1 Pro guessed Breakout in under 10 minutes via OpenRouter.

Engineering · Nov 2 · 255 points on HN
Scaling Git at OpenAI: Pando, a Git backend built for agent-scale pushes

OpenAI says Codex-driven parallel work pushed its monorepo's Git serving below 90% reliability at times, so it built Pando, a Git-protocol-compatible backend that has served production traffic since April. Pushes to different branches proceed independently under causal consistency (one ref pointer is the only contended key), and fetches reuse stored packfiles served through regional caches instead of computing a pack per client. Background compaction, modeled on LSM-tree levels, merges small packs so fetch planning scales logarithmically.

OpenAI reports a median push latency cut of nearly 5x, nearly a petabyte of Git data served per day, more than 99% cache hit rates on pack delivery, and 10 Gbps links saturated on standard cloud VMs. It says Pando was built with Codex in 10 weeks, and that GPT-6 Astra agents wrote Lean and TLA+ models to find bugs. The tradeoff is that readers of several branches may see them at different points in time. OpenAI says it is exploring ways to share the technology.

Revolut says self-hosting GLM on 56 B200s cut coding-assistant costs 90%

StartupHub.ai summarizes a conference talk in which Revolut says it moved 2,000 engineers from metered Anthropic and OpenAI APIs to GLM 4.5 on 56 Nvidia B200 GPUs, at about 30 cents per million tokens. The speaker reported time to first token falling from over 10 seconds to 1.6 seconds, and, after tuning context limits, quantization and parallelism, an 88% performance gain for 76% more demand with no added GPUs. Cited details include a 256k context cap, NVFP4 saving about 40% of GPU footprint versus FP8 with no precision loss for this use, and tensor-parallel 8 rather than 4 to fit the KV cache.

The article notes the 30-cent figure excludes cloud spend, staffing and observability, and that image tasks are routed to Gemini-class models. The coverage dates to Oct 29; the HN thread is from Nov 3.

Engineering blog · Nov 1
Carlini: a modern Stockfish port on a 1995 Pentium Pro would have beaten Kasparov

Nicholas Carlini ported Stockfish to a 200 MHz Pentium Pro with 64MB of RAM and estimates its strength at 3300 ± 87 Elo at classical time controls, versus roughly 2700 for Deep Blue. His experiments attribute 720 of the 1,335 Elo gained since 1996 to better algorithms (search techniques, NNUE evaluation) rather than faster hardware. Crafty 11.13 with modern techniques added rose from 1999 to 2718 Elo at one second per move on the same machine.

The Apache-2.0 repository describes a framework that builds an ontology from enterprise metadata, reconciles metric definitions across systems, and serves that context to agents through MCP, CLI and API. 🧠 Today's Lesson
Quantization: what "NVFP4 saves 40% versus FP8" actually means, and why it frees memory for the KV cache

Quantization stores each weight in fewer bits. FP8 uses 8 bits per weight; a 4-bit format uses half that. Naively, 4-bit values cannot span the range of real weights, so formats add scale factors: weights are grouped into small blocks, and each block stores one shared scale. NVIDIA's NVFP4 stores 4-bit floating-point values with a scale for every 16 weights, plus a per-tensor scale, so the effective cost is a little over 4 bits per weight rather than exactly 4.

That overhead is why savings are less than 50% in practice. Revolut's reported figure of about 40% GPU footprint versus FP8 sits below the 50% ceiling, and the model is not the only thing on the GPU: activations, buffers and the KV cache take memory that weight formats do not shrink.

The KV cache is the real constraint for long-context serving. It grows with sequence length times concurrent requests, so every gigabyte freed from weights buys room for more tokens in flight. This is also why the talk's tensor-parallel 8 versus 4 point matters: splitting across more GPUs gives each one a smaller share of the weights, leaving more memory per GPU for cache.

The catch is accuracy: smaller formats can lose quality on some tasks, so the claim of "no precision loss" holds only for the workload tested. Evaluating on the production workload before switching is the standard check.
