Today's Lesson

Prompt caching: why a cache read costs ~10% of an input token

Anthropic just halved Sonnet 5.5's cache-read price to $0.10/M against $2.00/M for fresh input. Why is a cached token so much cheaper? Because the expensive part of a prompt is prefill: computing keys and values for every token at every layer. That KV cache is deterministic given the exact token prefix, so the provider can store it and skip the compute next time.

The catch is that caching is prefix-based. Reuse only works if everything up to a point is byte-identical, so a timestamp or reordered tool list near the top invalidates everything after it. Structure prompts as stable parts first (system prompt, tool definitions, documents), volatile parts last (the user turn, scratch state).

Cost math for an agent loop: say a 50K-token context grows by 1K tokens per step over 30 steps. Uncached, you pay full price on ~1.5M input tokens total. Cached, you pay a write premium once, then 10% on the repeated prefix. Haiku 5.5's write price is 1.25x input ($0.125), so a prefix reused even twice pays for itself. Also remember cache entries expire after a short TTL, so a long pause between steps can mean paying for a rewrite.
