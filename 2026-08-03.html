Today's Lesson
Prefill–Decode Disaggregation: why big inference clusters split the two phases across separate hardware

Every LLM request runs two computationally distinct phases. Prefill processes the full input prompt in parallel to build the KV cache — it's compute-bound, saturates GPU SMs beautifully, and completes quickly. Decode then generates one token at a time, loading weights and the growing KV cache from VRAM on every step — it's memory-bandwidth-bound and takes as long as the output is tokens.

Colocating both on the same hardware forces a bad tradeoff: when prefill fires for a new request, it stalls the decode pass for every other in-flight request, spiking time-to-first-token (TTFT) for arrivals. Prefill-decode (PD) disaggregation splits them onto separate node pools. Prefill runs on compute-dense hardware (H100 SXM, B100); decode runs on memory-bandwidth-heavy hardware (H200, or more GPUs with slower compute). Each pool scales independently: add decode nodes to fix throughput, add prefill nodes to fix TTFT.

This is production reality now, not research. DeepSeek's API, Google Gemini's serving stack, and AWS SageMaker HyperPod all use PD disaggregation. vLLM and SGLang both support it natively. The main operational wrinkle is the KV-cache transfer between the two pools — which is why network topology (NVLink vs. InfiniBand vs. ethernet) matters so much and is still an active research area. There's a paper on exactly this in today's arXiv feed: Topology-Aware Data Movement for Disaggregated GPU Inference. DeepSeek-V4-Flash-0731 shipping with DSpark speculative decoding is a complementary trick: a small draft model generates candidate tokens on the decode side, letting you use the memory-bandwidth budget more efficiently between KV transfers from the prefill pool.

Practical upshot: if you're self-hosting a large MoE (Qwen3.8, DeepSeek V4) and hitting latency ceilings under load, PD disaggregation is the architectural lever to reach for before you throw more uniform GPU memory at the problem.
