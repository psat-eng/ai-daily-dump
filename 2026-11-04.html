🔥 What's Hot Right Now
Hardware · Nov 1 · 3 days old, 437 points on HN Nov 4
RTX Spark laptop runs GPT-OSS-120B at 65 tok/s on Windows but 14 tok/s on plugged-in Linux

A MindStudio write-up, dated Nov 1, benchmarks an MSI RTX Spark laptop and reports 65.4 tokens per second on Windows, 65.1 on WSL and 13.9 on native Linux while plugged in. The same Linux install reaches 61 tok/s on battery. In a vLLM test with eight concurrent clients, WSL delivered 127 tok/s against 39.5 on native Linux.

The author attributes the gap to a Windows-only "Nvidia Platform Controller" that splits power between CPU and GPU: with it disabled on Windows, throughput fell from about 83 to 32 tok/s and clocks from about 2 GHz to 786 MHz, matching Linux. The write-up says the GPU power-state firmware table is encrypted and only Windows can decrypt it, so a fix would have to come from Nvidia's Linux driver work. It also notes the laptop reserves 96GB for the GPU by default and only Windows exposes a setting to change the split.

🚀 New Releases & Updates
Open weights · Nov 4
Moonshot AI publishes Kimi K3.1 Pro weights: 2.8T parameters, 104B active, 1M context

The model card lists a mixture-of-experts design with 896 experts (16 selected per token plus 2 shared), 93 layers mixing 69 KDA linear-attention layers with 24 Gated DeepSeek Sparse Attention layers, a 1,048,576-token context, and MXFP4 weights with MXFP8 activations from quantization-aware training. The license is a Kimi-specific one (kimi-k3.1-pro) rather than a standard open-source license. The model was announced in October with weights promised by Nov 4; RuntimeWire reports they landed on Nov 4.

Moonshot's launch post reports 65.7% on Terminal-Bench 4.0 (versus 66.4% for Claude Opus 5.5 and 58.2% for GPT-6 Astra) and 92.7% on BenchCAD with tools. It also says it removed cyber-related data from mid-training and RL, which cut its internal exploit-benchmark score from 90.5% to 81.0%. All figures are vendor-reported, and the model card's own table shows it trailing on Program Bench and Terminal-Bench-Science.

🛠️ Flip Tech Watch
Flip Tech Watch · Nov 4
Kimi K3.1 Pro: a reported drop in factual-error rates, plus zero data retention on the API

Moonshot says K3.1 Pro's claim-level hallucination rate on its internal "Hallu Bench Hard" stress set fell from 23.4% to 8.3% versus K3, and that Zero Data Retention is available to API customers. It also reports state-of-the-art 64.4 on OfficeQA Pro v2, a retrieval and cross-document verification benchmark. All numbers are Moonshot's own.

Flip angle: Knowledge-base answers on ecommerce calls depend on the model not inventing policy details such as return windows or order status. The zero-retention option matters for caller data sent to a hosted API. The 2.8T-parameter weights are impractical for in-house serving, so the first test is the hosted API as a fallback or QA-grader model on a sample of escalated calls, measuring unsupported-claim rate against the existing KB. Caveat: the stress set is deliberately adversarial and not a proxy for call traffic, and latency for a reasoning-heavy 1M-context model has not been checked against voice turn-taking budgets.

🧠 Today's Lesson
Why decode speed depends on memory bandwidth, and what a 5x slowdown at the same memory size implies

Generating one token requires reading every active weight from memory once. At batch size one there is little arithmetic per byte read, so decode is usually bandwidth-bound: tokens per second is roughly memory bandwidth divided by bytes of active weights, a ceiling often called the roofline. This is why mixture-of-experts models run well on unified-memory machines. GPT-OSS-120B stores about 120B parameters but activates only a few billion per token, so each token reads only a small slice of the file.

Quantization raises the ceiling by shrinking bytes per weight, which is also why Kimi K3.1 Pro ships in MXFP4. Batching raises it differently: eight concurrent requests share one weight read, so vLLM's 127 tok/s with eight clients is aggregate throughput, not per-user speed.

The RTX Spark result is a useful puzzle. If decode were purely bandwidth-bound, a GPU clock falling from about 2 GHz to about 780 MHz should not cut speed 5x, since memory bandwidth is set by the memory system. A drop that large suggests something clock-sensitive is on the critical path: dequantization compute, attention kernels, kernel-launch gaps, or memory clocks tied to the same power state. The write-up does not say which. The practical takeaway is to profile before assuming: measure tokens per second alongside GPU and memory clocks, because a "bandwidth-bound" label can hide a power or scheduling problem.
