WorldTUI: a 360M model that pretends to be a terminal

Simon Edwardsson fine-tuned Qwen2.5-Coder-0.5B to act as a terminal with no shell or filesystem behind it: each keypress goes in and the model predicts which screen rows change. It can create files, run vim and tmux and play snake. The model works over a 333-token vocabulary, uses a COPY operation so a scroll costs about three tokens per row instead of roughly 96, and was trained on 336k synthetic sessions recorded from real shells in Docker.

For speed, rows are decoded in parallel and then checked by the same model in a speculative-decoding pass, which the author reports cut large-frame p95 latency on an RTX 4090 from 6.7 s to 0.87 s. Dropping the unused embedding rows took the model from about 494M to 360M parameters, and int4 quantization brought it to 208 MB for a WebGPU browser demo. The author is candid about limits: on his memory test it read back 9 of 13 values correctly, and combining familiar commands in new ways often breaks it.

Amazon: PHP2Shell exploitation attempts began October 17, four days before disclosure

Amazon Threat Intelligence says its MadPot honeypot network logged a PHP2Shell attempt on October 17 from an IP address tied to a commercial anonymization network, four days before CVE-2026-109618 and CVE-2026-109619 were made public. It reports further attempts from the early hours of October 21, with varying payloads suggesting multiple actors, and says the flaw is now being broadly exploited. It is unclear how the first actor learned of the bug, and Amazon says it is unclear whether any attempt would have succeeded on real systems.

Amazon argues that AI-assisted analysis makes it cheaper to turn a patch diff into a working exploit, and recommends measuring patch timelines for critical internet-facing bugs in hours. Its listed mitigations are upgrading PHP, since no configuration-only workaround covers both issues, and watching for PHP_SESSION_UPLOAD_PROGRESS in multipart uploads.

A skeptic's case: public PHP2Shell proofs of concept do not work on vanilla PHP

Developer Elias Taylor argues the PHP bug is real but far harder to exploit than Log4Shell or Heartbleed. He says the thousands of GitHub proofs of concept he looked at fail against a stock PHP instance, and that many lean on a separate local-file-inclusion flaw already being present on the target. He attributes the pattern to people trusting LLM-written exploits without running them. The post was written about ten hours after disclosure, and the claim is the author's own assessment. It sits against Amazon's report above of observed exploitation attempts, which does not say whether any succeeded.

Essay · Oct 20 · 167 points on HN
Asking an LLM for confidence: why the number cannot be trusted

Amrut Joshi argues that a confidence score has to reflect how much information supports a prediction and has to be checked against outcomes on the same kind of question. A model that writes "0.85" is generating a plausible continuation of the text rather than reading a gauge, so the number can change when the question is asked again or reworded, and is shaped by whatever the model wrote just before it. Pretraining calibrates next-token prediction, the post says, not the match between stated confidence and accuracy.

🛠️ Flip Tech Watch
Flip Tech Watch · Oct 20
Verbalized confidence versus measured confidence

The essay above argues that a self-reported confidence number is generated text, not a measurement, and that a trustworthy score needs outcome records for the same kind of question.

Flip angle: Any escalation or "should this call go to a live agent" decision that relies on the voice agent saying how sure it is would inherit this problem. The alternative is a score tied to logged outcomes, such as a classifier's probability checked against whether the call was later resolved or escalated. Caveat: the post is an argument, not an experiment, and the first test is to bucket past calls by whatever confidence signal exists and compare each bucket's actual resolution rate.

Flip Tech Watch · Oct 21
Trimming a small model's vocabulary and constraining its output

WorldTUI's author removed the unused embedding rows from a 0.5B model, decoded under a grammar that guarantees valid output, and quantized to int4 to reach 208 MB (see What's Hot above).

Flip angle: A fixed-label task such as intent routing needs only a small output vocabulary, so a fine-tuned small model with grammar-constrained decoding could return a valid intent label every time and run on modest hardware. Caveat: the demo is a research prototype with a synthetic data pipeline, its results are on the author's own benchmarks, and Flip's gain would depend on how a small model compares with its current router on logged calls.

🧠 Today's Lesson
Embedding tables: why a 0.5B model carries 136M parameters just for its vocabulary

The first layer of a language model is a lookup table with one row per token, and each row is a vector of the model's hidden size. Its parameter count is vocab_size × hidden_dim. For Qwen2.5-0.5B that is 151,936 tokens times a hidden size of 896, about 136M parameters, roughly a quarter of the whole model. The output layer that turns hidden states back into token scores has the same shape, so many small models tie the two and share one matrix.

That share is large only because the model is small. In a 70B model the same table is a rounding error; in a sub-1B model it is a major cost in memory and download size. It also sets the cost of the last step of every decode: scoring all 151,936 candidates for each generated token.

If a model will only ever emit a few hundred distinct tokens, most of the table is dead weight. Vocabulary pruning keeps the rows for tokens that will be used, renumbers them, and drops the rest. WorldTUI did this with a 333-token vocabulary, which accounts for most of the drop from 494M to about 360M parameters, before int4 quantization (about half a byte per weight) shrank it further.

The catch is that pruning is one-way: the model can no longer read or write anything outside the kept tokens. It suits fixed-format tasks such as classification labels or structured output, and it is a poor fit for open-ended chat.
