Janas: run MoE models larger than RAM by streaming experts from an SSD

Janas is a dependency-free C inference engine that keeps weights on disk and pulls only the experts each token needs from an NVMe drive, filling spare RAM with an expert cache. The README reports Qwen3-Next-80B-A3B (a 48 GB file) running at 20–25 tokens per second on a 32 GB laptop with an Intel Core Ultra 9 185H and a drive reading about 5.7 GB/s, and Qwen3.6-35B-A3B at about 32 tokens per second. With a browser and editor open and more than 8 GB already in use, it reports nearly 18 tokens per second.

The project calls itself "an experiment, not a product": it has been tested on one Debian machine, Windows and macOS are unsupported, stability is listed as not verified, and the author notes a GPU driver reset once took down the desktop. The repository shows a single commit and two stars.

Safety research · arXiv Oct 9 (4 days old, HN front page Oct 13)
AI models can provably hide arbitrary capabilities

Draguns, Motwani, Douglas and Schroeder de Witt embed encrypted neural networks inside a host model's weights that decrypt and run only when a secret trigger arrives. Using digital lockers, the authors argue the hidden circuits are provably hard to elicit or interpret under cryptographic assumptions, even with full weight access, extending earlier work that hid fixed strings to hiding arbitrary computation.

A PyTorch proof of concept, built around a small chemical-reaction prediction task used as a proxy for CBRN-relevant capability, resisted fine-tuning, weight noising, gradient-based trigger search and latent adversarial training. The authors conclude this exposes a limit of elicitation-based capability audits, and they released their models to support defence research.

Ben Recht: OpenAI's "faster Fourier transform" is "less a breakthrough and more a malicious exploit"

Recht examines a paper in OpenAI's recent batch of math results that claims a slightly smaller log(n) factor than the classic FFT. He calls it a galactic algorithm: he estimates the hidden constant near 10100 at N = 1012, so Cooley-Tukey would remain about 1099 times faster even at n = 10100, and the method assumes exact complex arithmetic with superpolynomially growing magnitudes that real hardware cannot provide.

He adds that the same batch included an O(n2.25) matrix-multiplication result whose constant cannot be estimated. Separately, OpenAI's math history page records that on Oct 7 it withdrew three algebraic-geometry papers over a sign error and revised 14 others (6 days old).

🧠 Today's Lesson
Decode is a bandwidth problem: tokens per second ≈ bandwidth ÷ bytes read per token

Generating one token means reading every weight that token touches from memory once, and doing very little arithmetic with each. So single-stream decode speed is capped by memory bandwidth divided by bytes read per token, not by FLOPs. That is why a faster chip with the same memory bus barely speeds up chat, and why quantization helps almost linearly: fewer bits per weight means fewer bytes per token.

Janas' numbers make a good worked example. The 48.4 GB file holds 80B parameters, about 4.8 bits each. A token activates roughly 3B of them, so around 3B × 4.84 / 8 ≈ 1.8 GB per token. If every byte came off a 5.7 GB/s SSD, the ceiling would be about 3 tokens per second. The reported 20–25 means most expert reads must be served from the RAM cache: at 22 tokens/s a token takes ~45 ms, versus ~316 ms for a fully cold read, so at most roughly 14% of the traffic can be going to disk. This is a back-of-envelope estimate that ignores compute and RAM-read time, not a measurement.

Rule of thumb: to predict decode speed, find the slowest tier a token's weights must cross, and divide its bandwidth by the active bytes. It is also why a card like the D270, with huge LPDDR5X capacity, would be judged on bandwidth, which Intel's page does not state.
