Open Weights · Sep 21–22
Xiaomi MiMo-V2.6-Pro: new #1 open-weights model, MIT licence, RL environments open-sourced

MiMo-V2.6-Pro is a 1.02T-total / 42B-active MoE. It is natively omnimodal (text, image, video and audio in one checkpoint) with a 1M-token context. It debuted at 46 on the Artificial Analysis Intelligence Index, the highest of any open-weights model, at roughly $0.435/$0.87 per M tokens via API. There is also a 309B/15B-active Flash variant. The community is paying most attention to the RL stack: Xiaomi is releasing its environment code and training recipes for coding, cyber, agent and web-dev tasks. The reported RL run took about 130 hours and about $2.6M.

To serve it: vLLM has day-0 support and a recipe. The weights are stored as mxfp4 and computed in FP8, giving a 566 GB checkpoint. That needs 8×H200 (TP8) or 4×MI355X (TP4). Stable vLLM ≤0.29.0 can't load it, so use the vllm/vllm-openai:mimo-v26 image or a nightly. It ships with a built-in DFlash drafter that proposes 7 tokens per pass. (See today's lesson on the mxfp4 format.)

HN #6 · today
Claude Code only read AGENTS.md when telemetry was on (now fixed)

Claude Code 2.1.277 added an AGENTS.md fallback, but the loader was gated on a remote feature flag (tengu_agents_md_mod) that defaulted to false. With DISABLE_TELEMETRY or CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC set, or when running through Bedrock, Vertex or a gateway, the flag could never resolve. The file was then skipped silently. The author proved it with a canary word. The HN title now says "[fixed]". The workaround still works everywhere: a one-line CLAUDE.md containing @AGENTS.md.

The broader lesson: if your agent seems to ignore its instructions, first check that the instructions reached the context window at all, before you rewrite the prompt.

💡 Today's Lesson
MXFP4: why MiMo is "stored in 4-bit, computed in FP8"

MXFP4 is a microscaling format from the OCP MX spec. Weights are grouped into blocks of 32. Each element is a 4-bit float (E2M1), which can only represent ±{0, 0.5, 1, 1.5, 2, 3, 4, 6}. Each block shares one 8-bit scale (E8M0), which is a pure power of two. That works out to 4 + 8/32 = 4.25 bits per weight.

Why a float grid instead of INT4? Weights cluster near zero. The FP4 grid packs more levels near zero and fewer out at the tails, so typical values lose less precision than they would on INT4's evenly spaced levels. The power-of-two scale is cheap to apply because it's just an exponent add. The downside is coarseness: the block's range can only change in factors of 2. NVFP4 addresses this with 16-element blocks and an FP8 (E4M3) scale.

Why store in one format and compute in another? Decode is memory-bandwidth-bound, so the main win is moving fewer bytes, even if the math runs at higher precision. Hopper GPUs (H200) have no FP4 tensor cores, so the kernel unpacks MXFP4 weights to FP8 in registers and runs FP8 GEMMs. Blackwell and AMD CDNA 4 (MI355X) can run MXFP4 matmuls natively, which is why the vLLM recipe needs no load-time requantization on MI355X.

Sanity check: 566 GB × 8 bits ÷ 1.02T params ≈ 4.4 bits per param. That is slightly above 4.25 because some parts, such as the router, stay in bf16. When a model card lists "storage dtype" and "compute dtype" separately, the first sets how much VRAM you need and the second sets which kernels and GPUs you can use.
