📖 Today's Lesson
Speculative Decoding: how to get more tokens/sec without changing model output

Standard autoregressive decoding is sequential: the model runs a full forward pass to produce one token, appends it, runs again, repeat. That means your GPU is mostly waiting — each step needs the previous step's output. Speculative decoding breaks this bottleneck without changing what the model produces.

The idea: use a small, fast "draft" model to speculatively generate a batch of K candidate tokens in one shot. Then run the full "verifier" model on the entire batch in a single parallel forward pass. Because the verifier can process all K positions simultaneously, you pay roughly one forward-pass cost to verify K tokens instead of K forward-pass costs. Any token the verifier agrees with is accepted; the first disagreement truncates the batch and you resample from there. Statistically, if the draft model is good, you accept most tokens — so you get K tokens for roughly 1× verifier-pass cost instead of K×.

The key insight is that verification is parallelizable but generation is not. The verifier runs attention over all K positions at once; it's just a forward pass on a longer sequence. No new math is needed — accepted tokens are provably identical to what the verifier would have produced autoregressively.

Multi-Token Prediction (MTP), now in llama.cpp, is a related but different trick: rather than a separate draft model, the base model itself is trained to output K token predictions per forward pass. It acts as its own drafter. llama.cpp's MTP support is showing 1.5–1.7× throughput gains on M-series Macs — no second model needed, just a GGUF with the MTP heads baked in.

The practical tradeoff: speculative decoding shines when your workload is latency-bound and you have spare GPU memory for a draft model. It underperforms when GPU memory is tight or when the draft acceptance rate is low (e.g., highly creative or unpredictable outputs). For serving, it's usually more impactful on per-request latency (TTFT + generation speed) than on aggregate throughput, where continuous batching already keeps the GPU busy.
