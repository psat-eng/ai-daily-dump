SGLang day-0 for Qwen3.8-Flash-Next — QSA kernel, IndexShare MTP, HyperConnection kernels
Aug 26
The LMSYS blog post is unusually detailed and worth reading if you serve large MoE models. Highlights: IndexShare MTP reuses the QSA block-selection across draft decode steps so you only run the indexer once per MTP iteration instead of N times — big savings at long context. The HyperConnection (Mix/Combine) kernels get a 2.05× speedup at decode batch sizes via a split-K CuTe GEMM fused with SiLU/Sigmoid gating. The 51B N-gram embedding table is pinned to host memory and asynchronously prefetched per token — on H200 TP4 this freed ~23.5 GiB per GPU and increased KV cache capacity by 78.5% with effectively zero throughput loss. Launch commands and TP configs are in the SGLang cookbook.

📖 Today's Lesson
MoE Routing & Active Parameters: Why "125B / 6B active" Is the Number That Actually Matters for Inference

Mixture-of-Experts models have two numbers that mean completely different things. Qwen3.8-Flash-Next has a 125B backbone with ~180B total weights on disk — but only 6B parameters activate per forward pass. For inference capacity planning, these two numbers drive different constraints.

The architecture: instead of one large dense FFN, an MoE model has N "expert" sub-networks. A learned router (a small linear layer) scores each token's hidden state and selects the top-K experts to compute. Qwen3.8 uses 512 experts, activating top-10 routed + 1 shared per token, totaling ~6B active. Everyone else sits cold.

For inference this means: memory bandwidth ≠ compute. You still need to load all ~180B weights into VRAM (or offload to NVMe), but your FLOPs per token are those of a dense ~6B model. This is the "free lunch" side of MoE: quality like a large model, compute like a small one. The cost: VRAM pressure like the large model, which is why Qwen3.8's FP8 checkpoint at 172.78 GiB needs a TP2 minimum on GB300.

Qwen3.8 adds a twist: the 51B N-gram embedding table (PLE) is a hash-addressed lookup over bigrams/trigrams that lives in pinned host memory — it never permanently occupies GPU VRAM. SGLang gathers only 16 rows per token via async prefetch on a second CUDA stream, overlapping with the first decoder block. This is why it freed 23.5 GiB per GPU in benchmarks with zero throughput penalty.

Rule of thumb: active parameter count → your throughput/compute budget. Total parameter count → your memory budget. The N-gram table is a third category: it contributes to capacity but can be almost entirely offloaded.
