Meta Muse Glimmer 30B — an open-weight agent model that runs on a single consumer GPU

The #1 story on HN yesterday. Meta Superintelligence Labs dropped Muse Glimmer, a 30B-parameter open-weight model purpose-built for autonomous agentic tasks on consumer hardware. It runs inside 24GB VRAM (RTX 4090 / 5090, Mac M4/M5 Pro) and ships under Apache 2.0. Architecture: a 28B text decoder fed by a 2B ViT-style vision encoder, distilled from the larger Muse Spark.

The interesting engineering detail: Meta baked DFlash speculative decoding in from day one, delivering a 3.1× speedup on an RTX 5090, 1.8× on M5 Max. The 4-bit GGUF quant lands under 20GB. Unsloth and official meta-models GGUF repos are already live on Hugging Face. Supports Ollama, LM Studio, vLLM, SGLang, ExLlamaV2, and MLX out of the box. Early benchmarks put it ahead of Gemma4-31B and Qwen3.6-27B on several evals.

✅ New Releases & Updates
Claude Code Announced Aug 9 · Rolling out Aug 14
Claude Code Auto Mode becomes the default for Pro, Max, and Team plans

Anthropic is flipping auto mode on by default for new Claude Code sessions starting August 14. Instead of prompting for approval on every tool call, a classifier evaluates each action for whether it's irreversible, destructive, or out-of-scope. If blocked, Claude tries a safer alternative or asks; after repeated blocks it falls back to manual mode. Anthropic's internal study found humans caught 13.6% of dangerous commands while the classifier caught 89%. Enterprise and API customers stay opt-in for now, with a general rollout planned within a month.

Docker GA · Aug 3
Docker Sandboxes — disposable microVM isolation for AI coding agents

Docker Sandboxes give each AI coding agent (Claude Code, Codex, Copilot CLI, OpenCode, Kiro) its own isolated microVM — private filesystem, its own Docker daemon, isolated network — accessed via a new sbx CLI. Unlike containers that share the host kernel, a microVM emulates hardware and runs its own kernel, creating a hard boundary around untrusted agent-generated code. "Sandbox kits" let you bake in repeatable tooling, credentials, and config so each fresh VM starts ready to work.

Mistral / Safety Released Aug 4–7
Mistral Shieldstral 1.0 — 3B open-weights safety classifier with runtime policy injection

Shieldstral reframes content moderation as question-answering: you hand it your moderation policy in plain language at inference time, no retraining or fine-tuning needed. Built on Ministral-3B with a Pixtral vision encoder, trained on 54.1M contrastive pairs across 12 languages. Single 16GB GPU. Scores 99.4% on HarmBench, 97.7% on VLGuard — matching or beating guardrail models up to 7× its size. Apache 2.0. Genuinely useful if you're shipping agents that need tunable content policies without the overhead of full model fine-tuning.

📖 Today's Lesson
Grouped-Query Attention (GQA): why Muse Glimmer fits in 24GB when vanilla transformers wouldn't

Standard multi-head attention (MHA) gives every attention head its own key and value matrices. A 30B model with 40 heads generates 40 separate KV caches per token — massive memory pressure, especially as context grows. For a 32K-context request with a batch of 8, KV cache alone can eat tens of gigabytes.

Grouped-Query Attention solves this by sharing key and value heads across groups of query heads. Instead of 40 KV heads, you might have 8 — so each group of 5 query heads shares a single K and V. This cuts KV cache memory proportionally (in this example, 5×) with almost no quality loss, because empirically the KV projections carry much less information diversity than the Q projections.

The extreme version — Multi-Query Attention (MQA) — uses just one shared K and one shared V for all query heads. GQA is the sweet spot: Llama 3, Mistral, Gemma, and now Muse Glimmer all use it. The reason Muse Glimmer runs inside 24GB (including weights + KV cache for a working context) is largely this: its 8 KV heads vs 28 Q heads give a 3.5× KV memory reduction vs a naive MHA design of the same parameter count.

Practical implication: when evaluating whether a model fits your GPU memory budget, the KV cache contribution scales with context length × batch size × number of KV heads × head dimension × 2 (for K and V) × dtype bytes. A model with fewer KV heads lets you run longer contexts or larger batches before spilling to CPU.
