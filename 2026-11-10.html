Anthropic releases Claude Fable 5.2 and Mythos 5.2

Anthropic describes Fable and Mythos as the same underlying model, with Fable carrying cyber and biology safeguards for general availability and Mythos offered through verification programmes. It reports output up to 30% faster than the 5.1 models, pricing of $8 / $40 per million input / output tokens (Simon Willison notes this is 20% below Fable 5.1's $10 / $50), and an optional fast mode at $16 / $80 that speeds generation up to 2.5x.

On Anthropic's own table Fable 5.2 scores 49.1% on FrontierCode 2.0 at Xhigh effort versus 45.5% for Opus 5.5, and the company says High effort matches Opus 5.5's best for about half the cost per task. Anthropic still recommends Opus 5.5 as the daily driver. Artificial Analysis ranks Fable 5.2 first on its index at 65. Anthropic's new prompting guide adds one concrete tip: telling the model the codebase is its own made it merge repeated code in about half of small test tasks, against under a tenth without that sentence.

Meta reports that it matches Haiku 5.5's best Artificial Analysis score (36) at about a third of the cost and sits on the index's cost-per-task Pareto frontier; on Meta's table it scores 37.8 on AutomationBench-AA against 13.9 for Haiku and 20.2 for Luna. Research · Nov 10
DeepMind's AlphaProof Code formally verifies the implementation of the Signal protocol

DeepMind says human experts and models translated Signal's security goals into formal specifications, then Gemini Carbon agents wrote more than six million lines of Lean proving the compiled code meets them, with agents flagging about 1% of the proof for human review. The whole effort took four weeks. As a check, the team reintroduced two real, previously fixed bugs, and the system produced machine-checked proofs that those versions were insecure. DeepMind calls it the first verification of a widely deployed protocol's implementation at this depth by any method.

Engineering · Nov 9 · 586 points on HN
Amazon engineers replace Sonnet 4.6 with a decision model in a giant internal ticketing system

Two engineers describe moving 20-way ticket labelling from Sonnet 4.6 to Strands Decider E4B (a Gemma 4 build) on single-A10G SageMaker instances. Their measurements: 897 ms versus 4,215 ms per call, 2,010 versus 6,724 tokens per ticket, and roughly $500 versus $22,200 per million tickets at list prices. Production label descriptions exceeded the model's 4,096-token window, so each label was rewritten as a one- or two-sentence criterion plus a "none" option.

Two details stand out: reordering JSON keys in the same input shifted output probabilities by up to 0.19, so requests are now sent with sorted keys; and an AppConfig switch with BEDROCK, DUAL and DECIDER modes let both models run on live traffic before cut-over, with rollback a 45-second config change.

🛠️ Flip Tech Watch
Flip Tech Watch · Nov 9
A production playbook for swapping an LLM classifier for a decision model

The Amazon write-up (see "Also Worth Reading") is the clearest public account so far of a decision model taking over a high-volume labelling job: a closed label catalog rewritten as short criteria, a confidence threshold tuned on held-out tickets, and a three-mode switch that ran both models in parallel on live traffic before cut-over.

Flip angle: Post-call intent and escalation-reason tagging has the same shape: a fixed catalog, high volume, and no need for explanation text. The DUAL-mode pattern maps directly onto the QA pipeline, labelling with the current LLM while logging the decision model's answer for disagreement review. Caveats from the authors apply: long transcripts must be trimmed to a few thousand tokens, and key ordering in structured inputs should be fixed before comparing runs.

Flip Tech Watch · Nov 9
Muse Ember as a cheap subagent for extraction and routing

Meta positions Ember for "the work agents repeat all day": tool calls, routing, extraction and long-document parsing, at $0.10 / $0.50 per million tokens with cached input at $0.004 below 200k tokens, per Willison's table.

Flip angle: Candidate for non-latency-critical steps such as order-detail extraction from transcripts, knowledge-base article drafting from escalated calls, and call summaries, where it would be benchmarked against Haiku 5.5. Benchmarks are Meta's and Artificial Analysis's, not voice workloads, and in-call latency on the Meta Model API is unmeasured; a side-by-side on a few hundred labelled calls is the first test.

Flip Tech Watch · Nov 9-10
The Fireworks incident as a vendor-risk checklist for inference providers

Notion's disclosure (see "Also Worth Reading") shows how transcripts sent to a third-party inference host for a secondary analytics feature became the exposed data, even without user or workspace labels attached.

Flip angle: Call transcripts carry order numbers, addresses and payment-adjacent details. The practical takeaways are an inventory of which inference providers receive raw transcripts, PII redaction before any analytics or classification job leaves the core stack, and confirming retention terms with each provider. Notion has not said how the Fireworks systems were accessed, so the root cause is still open.

🧠 Today's Lesson
Shadow mode: testing a replacement model on live traffic before it makes a single decision

Offline evals use a frozen test set, and production traffic drifts away from it: new products, new phrasing, unusually long inputs. Shadow mode (or "dual-run") closes that gap. The incumbent model keeps making the real decision, while the candidate receives the same input in parallel and its answer is only logged. Nothing a customer sees changes.

The output is a stream of disagreements, which matter more than the agreement rate. If two models agree on 94% of items, the remaining 6% are where one of them is wrong, and reviewing a sample of those shows which. It often reveals that the incumbent was the one making mistakes, and surfaces input quirks no offline set contained, such as the key-ordering sensitivity in the Amazon write-up.

Three practical details make it work. Run the candidate asynchronously so its latency cannot slow the live path. Log both answers with a shared request ID plus the candidate's confidence, so disagreements can be sliced by confidence bucket. And keep the switch in runtime config, with modes like incumbent, shadow and candidate, so cut-over and rollback take seconds rather than a deploy. Shadow mode costs double inference for its duration, which is why it usually runs on a sample of traffic for days, not forever.
