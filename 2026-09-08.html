🎓 Today's Lesson

Prefix Caching: Why Your Agent's Second Call Is Much Cheaper Than Its First

When an LLM processes a prompt, it builds a KV cache — key-value tensors for every token in the context window. These are expensive to compute. Prefix caching (sometimes called prompt caching) lets the serving layer reuse that computed KV cache across requests that share a common prefix.

In practice: if every call to your agent starts with a 4,000-token system prompt, and you're making 1,000 calls per hour, the serving infrastructure (vLLM, SGLang, or your API provider) can compute those 4,000 tokens once and cache the result. Subsequent requests that start with the same prefix skip that computation entirely — TTFT drops and cost per call falls, often dramatically.

The catch: cache keys are exact prefix matches. Even one changed token invalidates the cache. This means prompt design discipline matters for cost: put stable content (instructions, tool schemas, long documents) first, and put dynamic content (the user's message, retrieved chunks) at the end. A common mistake is interpolating session IDs or timestamps into the system prompt, which defeats caching for every request.

On the API side, Anthropic's cache_control parameter, OpenAI's implicit prefix caching, and Google's context caching all implement variants of this. vLLM's enable-prefix-caching flag does the same for self-hosted deployments. At scale — especially in agentic loops with long, repeated context — prefix caching is one of the highest-ROI infrastructure choices you can make.
